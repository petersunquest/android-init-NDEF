## 摘要

本文提出一个运行在 CoNET 上的去中心化挂单交易所。用户签名挂出限价单，由 CoNET 矿工组成的撮合委员会完成拆单与撮合，DLE 档案组对每个撮合批次做独立重放和最终确认，最后由 CoNET L1 结算合约逐笔核验用户签名，把资产从卖方钱包直接转给买方。

三条核心规则：

1. **非托管。** 交易所没有金库，不持有用户资金。用户只授权 DLE 结算合约在成交时按订单签名的上限转出和转入资产。资金在成交前始终留在用户自己的钱包里，用户随时可以撤回授权【已决定】（2026-10-25）。
2. **矿工以手续费为动力。** 拆单和撮合由矿工完成，矿工按每笔成交额收取 **0.01%** 手续费作为报酬【已决定】（2026-10-25）。
3. **撮合者没有定价权。** 撮合规则是确定性的，写在账本的状态机里。档案组逐批重放，结果不一致就拒绝。L1 结算时再逐笔核验用户签名和限价。矿工能决定收录哪些订单，但不能改价格、改数量、改收款人，也不能动用户的钱。

撮合采用**频繁批量竞价**：每个批次内的订单按统一清算价成交，批次内的先后顺序不影响价格，以此降低抢跑空间【本文拟议】。每个交易对是一条独立的 DLE 账本，各交易对并行运行。

批量竞价意味着成交要等到下一个批次。对需要立即锁定价格的交易者，本文在第 10 章讨论一条“快速通道”：由用户自愿提供流动性，签署限时有效的承诺报价，吃单方即时锁价，流动性提供者赚取快速交易手续费。这一部分是【待讨论】，第 10 章列出了几种方案、本文的建议和需要决定的事项。

本文所依赖的 DLE 组件尚未进入生产。DLE 的档案组生产签名目前被规范禁止，30 天试运行的最终评估是“部分成功，未达标”（DLE 修订说明，2026-09-23）。本交易所需要在 DLE 中新增一个“市场类”账本，这是 DLE 协议修订，不是现有规则的重新解释。本文不承诺上线时间、成交速度、流动性深度或任何收益。

> 阅读范围：面向 DAO 投票者、矿工、做市方、DLE 规范维护者与审计者。文中示例参数仅用于演算，不是上线参数。

## 1 定位与范围

### 1.1 要解决的问题

现有去中心化交易多用 AMM 曲线定价。研究页已经说明，挂单簿可以避免几类 AMM 特有的问题：价格由明确的买卖报价决定，而不是由曲线决定；大额交易吃掉的是可见深度，而不是沿曲线滑动；做市方自己决定报价、库存和撤单，不必把资金放进池子承担无常损失。

挂单簿也有自己的问题：深度薄时价差更大；撮合网络带来排序、审查、可用性和抢跑风险。本文不主张挂单簿在所有情况下都优于 AMM，目标是在 CoNET 上提供一种不依赖曲线、不托管资金、由矿工网络撮合的交易方式。

### 2.3 为什么需要新增“市场类”账本

DLE 现行只有三类账本：资产类、存储类、交易类，类别在创建时固定，账本内没有通用虚拟机，账本之间不能自由调用【DLE 现行】（DLE §4.2、§10）。交易类账本只处理一个 NFT 式标的的出售，不定义交易对范围的排序、跨多个订单的部分成交、撤单竞态和批量结算。研究页也写明，不能把现有交易类重新解释为同质化代币交易所。

本文因此提出**市场类账本**（classId = 4）【本文拟议】：

- 与其他类别一样，绑定唯一的 L1 NFT，没有虚拟机，状态转移函数固定；
- 一个市场类账本只服务一个交易对；
- 状态机内含确定性的撮合算法，档案组重放时必须得到完全相同的成交结果；
- 账本不持有资金，只产出“谁和谁以什么价格成交多少”的结果，资金转移在 L1 完成。

新增类别属于 DLE 协议修订，须由 DLE 规范维护者纳入 DLE 白皮书与配套规范后才能实现。在此之前，第 15 章给出一个不依赖 DLE 档案证书的过渡方案，供选择（附录 B，B-1）。

## 3 系统总览

### 3.1 角色

| 角色 | 由谁担任 | 做什么 | 收入 |
| --- | --- | --- | --- |
| 交易者 | 任何用户 | 授权结算合约，签名挂单、撤单 | — |
| 接单矿工 | 已登记、质押 CNET 的撮合矿工 | 经 L0 接收订单，验签，转发到该交易对的订单池，回执“已收到” | 本版不分成（附录 B，B-6） |
| 撮合委员会 | 每个批次从该档案组的按需矿工等待队列抽取 7 名，2 名候补【DLE 现行】 | 组装批次、拆单、撮合；其余成员独立复算并签名 | 0.01% 成交手续费（第 9 章） |
| 批次组装者 | 撮合委员会中按抽签顺序排第一的成员；失效时依次递补 | 从订单池取单、执行拆单与撮合、提出候选批次 | 手续费中的组装份额（第 9.2 节） |
| 档案组 | 该交易对账本所在的 5+2 档案组 | 重放、数据可用性检查、形成档案证书 | 可用性预算（第 9.6 节） |
| 结算中继 | 任何人，通常是想尽快拿到手续费的矿工 | 把批次与档案证书提交到 L1 结算 | 无专门报酬；手续费在结算后才入账 |
| 流动性提供者 | 自愿用户 | 挂出长期限价单；如第 10 章方案通过，还可签署快速通道承诺报价 | 价差；快速交易手续费【待讨论】 |

不同角色是否允许由同一运营者兼任，须由角色登记与利益冲突规则明确，不能默认每个 CoNET 矿工都可担任所有角色（研究页同样要求）。

  │ ① 一次性授权结算合约（有限额度）
  │ ② 签名订单 Order（EIP-712）

            档案组（5 活跃，4/5）

  核验档案证书 → 逐笔核验双方签名与限价 → 逐笔原子转账（卖方钱包 → 买方钱包）

### 3.3 三级确认

界面必须分开显示三种状态，不能把前一级显示成后一级（研究页要求）：

| 状态 | 含义 | 可能被推翻吗 |
| --- | --- | --- |
| **已收到** | 某接单矿工验签通过并回执 | 可能。回执不承诺收录或成交 |
| **已撮合（批次终局）** | 批次获得档案证书，成交结果写入账本 | 结果不会被改写，但 L1 转账仍可能因余额或授权不足而失败（第 4.4 节） |

## 4 资产授权与非托管结算【已决定】（2026-10-25）

### 4.1 原则

交易所不设金库，不保存用户余额，没有可以提取用户资金的管理员或撮合者密钥。用户的资产在成交之前一直在用户自己的钱包里。成交时，L1 结算合约在一笔交易内把卖方的基础资产转给买方、把买方的计价资产转给卖方。

结算合约只在执行 `settleBatch` 的那一笔 L1 交易内经手资金；该交易结束时，合约不持有任何用户资产。唯一留存在合约侧的是矿工已赚取、尚未领取的手续费（第 9.2 节）。

### 4.2 授权方式

用户授权分两层，缺一不可：

1. **代币授权**：用户对结算合约做 ERC-20 `approve`，或使用代币支持的签名授权（如 EIP-2612 `permit`）。钱包应默认建议有限额度，而不是无限额度。
2. **订单签名**：每笔订单的 EIP-712 签名规定了这笔订单最多卖出多少、最多支付多少、最差价格、截止时间。结算合约只在订单签名允许的范围内转账，且累计成交不超过订单数量。

代币授权只是“允许结算合约动用”，订单签名才是“允许按这个条件成交”。没有有效订单签名，即使用户授权了无限额度，结算合约也不能转出任何资产。

### 4.3 可上市资产

只有满足以下条件的 CoNET L1 ERC-20 才能上市【本文拟议】：

- 是 Treasury 规范代币或 CoNET 原生发行的规范代币，地址稳定，小数位固定；
- 转账行为精确：拒绝转账收费、弹性供应、转账回调、黑名单冻结等会改变实收数量或可被第三方阻断的代币，除非有经审计的版本化适配器证明结算精确；
- 升级权限公开、受时间锁或 DAO 约束；
- 其 CoNET 侧供应若依赖跨链证明（例如由 Base USDC 存入而铸造的 conet-USDC），则在该跨链证明被证明能拒绝伪造的源链消息之前，不得上市【已决定的通用门槛】（GB 白皮书 v0.3 第十七章）；
- 经 DAO 投票批准该交易对（第 13 章）。

免费 GB 不可转账、不可交易，不能上市【已决定】（GB 白皮书 v0.3 1.3、8.2）。收费 GB 可以上市，但以届时部署的新 GB 合约为准；新 GB、新 conet-USDC 合约目前均未部署。

### 4.4 非托管带来的竞态：成交可能失败

资金不锁定，就意味着同一笔余额可能同时支撑多笔订单，用户也可能在撮合之后、结算之前转走资产或撤回授权。因此：

- **撮合前预检**：每个批次引用一个已终局的 L1 区块号。撮合时，状态机按该区块的余额与授权，扣减该用户在本交易对已有挂单的占用，余额不足的订单不进入本批撮合。这一检查是确定性的，档案组可以复算。
- **跨交易对超额**：不同交易对是互相独立的账本，无法互相扣减占用。同一余额挂在多个交易对时，可能在结算时不足。
- **结算时的最终检查**：L1 结算以执行时的真实余额和授权为准。

所以，“已撮合”的成交不保证一定结算成功。本文的处理办法是**逐笔原子、批次不连坐**（第 8.2 节）：每一笔成交（一个买方对一个卖方）单独原子执行，要么双方资产都转，要么都不转；一笔失败不影响同批其他成交。

### 4.5 失败处理与约束【本文拟议】

| 情况 | 处理 |
| --- | --- |
| 某笔成交因一方余额或授权不足失败 | 该笔不转账、不收费。失败方的订单在 L1 标记为作废，剩余数量不再可成交 |
| 失败笔中守约的一方 | 账本在后续批次观察到 L1 结果后，恢复其被占用的剩余数量，订单继续挂在簿中 |
| 同一地址反复造成失败 | 账本按 L1 记录的失败次数降低其挂单上限；达到阈值后暂停该地址挂单一段时间（参数【待定】） |
| 是否要求挂单保证金 | 非托管模式下没有可扣的资金。是否引入一笔小额挂单保证金来惩罚恶意失败，列为待定（附录 B，B-5） |

失败笔会让守约方错过当批成交机会，这是非托管模式的固有代价。界面应向用户说明。

### 4.6 用户随时退出

用户不需要“提现”，因为资金从未离开钱包。用户想停止交易时，有三种方式，都直接在自己钱包或 L1 上完成，不依赖矿工或档案组配合：

1. 撤回或减少对结算合约的代币授权；
2. 在 L1 上调用撤单或提高最小有效 nonce，使旧订单全部失效；
3. 把资产转出到其他地址。

方式 2 进入 L1 收件箱，账本必须在后续批次处理（第 6.2 节）。方式 1、3 立即生效，之后涉及该用户的成交会在结算时失败，按第 4.5 节处理。

## 5 订单

### 5.1 订单结构

用户签名以下 EIP-712 结构【本文拟议】（字段名示意，字段集合与顺序在规范中冻结）：

```text
Order {
    version,
    marketId,          // 交易对的市场类账本 NFT id
    owner,             // 签名人；资产从此地址转出、转入此地址
    side,              // BUY / SELL
    baseAsset,
    quoteAsset,
    quantityLots,      // 总数量，单位为该市场的最小数量单位
    limitPriceTicks,   // 最差可接受价格
    minFillLots,       // 单次最小成交量，0 表示不限
    maxLotsPerBatch,   // 每批最多成交量（拆单上限），0 表示由市场参数决定
    timeInForce,       // GTC / GTD / IOC
    expiry,            // 绝对 unix 秒；GTD 与 IOC 必填
    feePolicyHash,     // 承诺所适用的手续费规则版本
    nonce,
    settlement         // 结算合约地址
}

domain = {
    name: "CoNET-DLE-Market",
    version: "1",
    chainId: 224422,           // CoNET L1
    verifyingContract: settlement
}
orderHash = EIP712Digest(domain, Order)
```

规则：

- `orderHash` 是类型化数据摘要，不是签名字节的哈希。EOA 使用低 s 值 ECDSA；合约钱包使用 EIP-1271。
- 撮合者不能替换资产、增加数量、放宽价格、延长期限、改变收款地址或重放已用 nonce。
- 不提供无价格上限的“市价单”。需要立即成交时，使用带最差价格的 IOC 单（研究页要求）。

### 5.2 订单类型

| 类型 | 行为 |
| --- | --- |
| GTC 限价单 | 未成交部分留在簿中，直到成交、撤单、失效或 nonce 作废 |
| GTD 限价单 | 同上，到 `expiry` 后失效。时间以批次引用的 L1 区块时间判断，不以矿工本地时钟判断【DLE 现行】（DLE §10.1） |
| IOC 单 | 只参加收录它的那一个批次，未成交部分立即作废 |
| 快速通道单 | 第 10 章讨论，【待讨论】 |

### 5.3 撤单

- **链下撤单**：用户签名 `Cancel{orderHash}` 发给接单矿工，被收录后在该批次开始撮合前生效。已在先前批次终局的成交仍然有效。
- **链上撤单**：用户在 L1 调用撤单或提高最小 nonce。它进入 L1 收件箱，账本必须按收件箱顺序处理（第 6.2 节）。在账本处理之前，结算合约仍会执行此前已终局批次中的成交，避免用户在撮合后撤单使整批结算失败。

### 5.4 价格与数量的整数表示

每个市场创建时固定三个参数：`lotSize`（基础资产最小数量单位，原生单位）、`tickSize`（每个 lot 的计价资产最小价格单位，原生单位）、价格上下限。一笔成交的计价金额为：

\[
\text{quoteAmount} = \text{lots} \times \text{priceTicks} \times \text{tickSize}
\]

全部是整数乘法，没有除法，因此成交金额本身没有舍入。手续费按第 9.1 节向上取整。

示例：GB（9 位小数）对 conet-USDC（6 位小数），取 `lotSize = 10^9`（1 GB）、`tickSize = 1`（0.000001 conet-USDC），价格 0.0102 conet-USDC/GB 即 `priceTicks = 10200`。此时最小价格变动约为价格的万分之一。参数仅为示例。

## 6 拆单与撮合

### 6.1 批次的产生

DLE 规则是“没有事件就没有区块”【DLE 现行】（DLE §3.2）。市场类账本的一个区块就是一个**撮合批次**：订单池里有新订单、撤单或 L1 收件箱事件时，才产生批次；没有就不产生。

每个批次是一个事件，按 DLE 的正常流程推进：档案组抽取撮合委员会 → 组装者提出候选批次 → 委员会 5/7 签名 → 档案组重放并形成档案证书【DLE 现行】（DLE §6.3）。

批次的输入包括：

- 引用的 L1 区块号（用于余额、授权、时间和收件箱）；
- 本批收录的新订单、链下撤单；
- 本批消费的 L1 收件箱区间及其累加哈希；
- 上一批次的状态根。

批次的输出（由状态机确定性算出）包括：清算价、成交明细、更新后的订单簿、状态根。

### 6.2 收录规则与抗审查

撮合是确定性的，组装者唯一能左右的是**收录哪些订单**。本文用两层机制约束这一点：

**硬性规则：L1 收件箱强制收录【本文拟议】。** L1 结算合约维护一个按顺序编号的收件箱，记录链上撤单、nonce 作废、L1 结算结果，以及用户直接提交到 L1 的订单（费用较高，作为抗审查兜底）。每个批次必须声明它消费到收件箱的第几条，并给出累加哈希；L1 结算时核对这个哈希与链上记录一致。规定：

- 批次必须按顺序消费收件箱，不能跳过；
- 收件箱中某条记录等待超过 `T_inbox` 个 L1 区块仍未被消费时，L1 拒绝结算任何引用更晚 L1 区块却仍未消费该记录的批次。

这样，提交到 L1 的订单和撤单最终一定会被处理，组装者无法长期审查。

**软性规则：多矿工接单与委员会轮换。** 订单经 L0 同时发给多个接单矿工；每个批次的委员会和组装者重新抽取。单个组装者遗漏订单，只能延迟它，不能长期阻止它。委员会成员可以对明显遗漏大量已广播订单的候选批次投拒绝票，但这依赖各自看到的订单池，不是确定性规则，不作为罚没依据。

**激励一致性。** 矿工按成交额收费（第 9 章）。遗漏可成交的订单就是放弃手续费，审查本身有成本。

### 6.3 拆单

本文的“拆单”指组装者把一笔大订单分成多次在不同批次中成交。它有三个来源：

1. **市场的每批上限**：每个批次的总成交额不超过 `B_max`，用于限制单个委员会经手的成交规模和单笔 L1 结算的 gas。超出部分顺延到后续批次。DLE 要求每个委员会的累计风险敞口不超过 \(E_{\max}\)【DLE 现行】（DLE §12.3.2），`B_max` 是本文为市场类账本给出的对应约束，具体如何计入 \(E_C\) 列为待定（附录 B，B-8）。
2. **用户自设上限**：订单的 `maxLotsPerBatch` 限制每批最多成交量，相当于冰山单或分批执行。
3. **部分成交**：在批量竞价的边际价位上，一笔订单可能只成交一部分（第 6.4 节）。

拆单不改变订单签名。L1 记录每个 `orderHash` 的累计已成交数量，任何时候都不超过 `quantityLots`。拆单的具体分配由状态机确定性计算，组装者不能自由选择把量分给谁。

### 6.4 撮合算法：频繁批量竞价【本文拟议】

每个批次对“簿中挂单 + 本批新订单”做一次统一价格竞价：

1. **候选价格**：所有参与订单的限价。
2. **成交量**：对每个候选价 \(p\)，需求 \(D(p)\) 为限价 \(\ge p\) 的买单剩余量之和，供给 \(S(p)\) 为限价 \(\le p\) 的卖单剩余量之和，可成交量 \(V(p)=\min(D(p),S(p))\)，且受 `B_max`、各订单 `maxLotsPerBatch` 和余额预检约束。
3. **清算价**：取 \(V(p)\) 最大的价格。并列时，依次取 \(|D(p)-S(p)|\) 最小者、离上一批清算价最近者、较低者。
4. **价格带**：清算价与上一批清算价的偏离超过 `priceBandBps` 时，本批只在价格带内成交（防止薄簿时的误操作和操纵，参数【待定】）。
5. **分配**：
   - 价格优于清算价的订单全部成交；
   - 限价恰好等于清算价的一侧（边际价位）按以下顺序分配剩余量：先到先得（以订单首次被收录的批次号为准，更早的批次优先）；同一批次收录的订单按剩余量比例分配；比例分配后的零头按 `keccak(orderHash ‖ batchSeed)` 升序逐 lot 分配，`batchSeed` 取自批次引用的 L1 信标随机数，签名时无法预知。
6. **成交价**：所有成交都按清算价执行。限价更优的一方获得价格改善。

选择批量竞价的理由：批次内订单的到达顺序不影响成交价，组装者无法靠调整顺序插队抢跑；成交量最大化也与矿工“按成交额收费”的激励一致。

代价：成交要等批次，不是逐单即时撮合；簿中挂单之间不会在批次之外成交。第 10 章讨论为需要即时锁价的交易者提供的补充通道。

是否改用批次内“价格—时间优先”的连续撮合，列为待定（附录 B，B-3）。连续撮合更接近中心化交易所的体验，但批次内顺序由组装者决定，抢跑风险更高。

### 6.5 成交配对

L1 结算逐笔执行，需要把批次结果拆成“一个买方对一个卖方”的成交对。配对是确定性的：

- 成交的买单按分配顺序排列，成交的卖单按分配顺序排列（价格更优者在前，再按第 6.4 节第 5 步的顺序）；
- 两个列表依次对齐，每次取双方剩余成交量的较小值形成一个成交对，直到全部配完。

每个成交对记录：买单 `orderHash`、卖单 `orderHash`、lot 数、清算价、计价金额、手续费。全部成交对组成 `fillsRoot`，写入批次状态根，由档案证书覆盖。

### 6.6 自成交防护

同一 `owner` 的买单和卖单若在同一批次都会成交，较晚被收录的订单本批不参与撮合（若收录批次相同，按 `orderHash` 较大者退出）。这只能防止同一地址的自成交；不同地址之间的对敲无法从协议上识别（第 12 章）。

## 7 市场类账本状态机【本文拟议，需 DLE 修订】

本章按 DLE 状态机元模型（DLE §10.1）写出骨架。编码、字段宽度、状态根和错误码沿用 DLE 规则；本章的具体取值须由 DLE 规范维护者审定。

### 7.1 状态

`None=0`、`Open=1`、`Halted=2`（熔断，只接受撤单与收件箱事件）、`DrainOnly=3`（退市过渡，只撤单、不撮合）、`Closed=4`。

### 7.2 事件

| 事件 | 编号 | 说明 |
| --- | --- | --- |
| `MarketOpened` | 0x1401 | 创世：绑定交易对、`lotSize`、`tickSize`、价格限、`B_max`、费率版本、结算合约，须与 L1 上 DAO 批准的市场记录一致 |
| `Batch` | 0x1402 | 一个撮合批次（第 6.1 节） |
| `MarketHalted` | 0x1403 | 观察到 L1 熔断条件（例如资产被暂停、跨链路由失效） |
| `MarketResumed` | 0x1404 | 观察到 L1 恢复记录 |
| `MarketDraining` | 0x1405 | 观察到 DAO 退市决议 |
| `MarketClosed` | 0x1406 | 退市过渡期结束 |

`Batch` 事件的载荷按顺序包括：`l1BlockNumber:u64`、`l1BlockHash:bytes32`、`inboxFrom:u64`、`inboxTo:u64`、`inboxAccumulator:bytes32`、`newOrders`（订单与签名列表）、`cancels`（链下撤单列表）、`batchSeed:bytes32`、`clearingPriceTicks:u64`、`fillsRoot:bytes32`、`bookRoot:bytes32`。

### 7.3 转移表（摘要）

| 当前 | 事件 | 前置条件 | 下一状态 | 账本效果 |
| --- | --- | --- | --- | --- |
| `None` | `MarketOpened` | L1 上存在 DAO 批准的市场记录且参数一致 | `Open` | 初始化参数与空订单簿 |
| `Open` | `Batch` | nonce 连续；引用的 L1 区块已终局且不早于上一批；收件箱按序消费且累加哈希正确；新订单签名有效、未过期、未作废；余额预检通过；未结算批次数不超过 `K_unsettled`；重算的清算价、`fillsRoot`、`bookRoot` 与候选一致 | `Open` | 更新订单簿、占用与成交记录 |

`/state`、`/nonce`、`/params`、`/lastClearingPriceTicks`、`/inboxConsumed`、`/lastL1Block`、`/lastSettledBatch`、`/book/bids/<priceTicks>/<orderHash>`、`/book/asks/<priceTicks>/<orderHash>`、`/orders/<orderHash>/remainingLots`、`/orders/<orderHash>/admittedBatch`、`/reserved/<owner>/<asset>`、`/failures/<owner>`、`/fills/<batchNonce>`（即 `fillsRoot`）。

沿用 DLE 元模型 `0x01xx`，市场类使用 `0x14xx`：`0x1401 ERR_MKT_BAD_SIG`、`0x1402 ERR_MKT_EXPIRED`、`0x1403 ERR_MKT_NONCE_VOID`、`0x1404 ERR_MKT_INBOX`、`0x1405 ERR_MKT_INSUFFICIENT`、`0x1406 ERR_MKT_MATCH_MISMATCH`、`0x1407 ERR_MKT_BATCH_CAP`、`0x1408 ERR_MKT_UNSETTLED_DEPTH`、`0x1409 ERR_MKT_PARAMS`。

## 8 L1 结算

### 8.1 `settleBatch` 步骤【本文拟议】

```text
settleBatch(marketId, batchNonce, batchHeader, fills[], orders[], signatures[], archiveCertificate)
```

任何人都可以提交。在一笔 CoNET L1 交易内：

1. 要求 `batchNonce` 等于该市场的 `lastSettledBatch + 1`，批次按顺序结算。
2. 按 DLE 交易类的规则核验档案证书：账本身份、批次载荷、数据可用性绑定、`membershipRoot` 与 L1 检查点一致、4/5 档案签名（或 DLE 规定的短证书检查点）【DLE 现行】（DLE §4.7）。
3. 核对批次声明的收件箱区间与累加哈希等于 L1 记录。
4. 核对 `fills[]` 的默克尔根等于档案证书覆盖的 `fillsRoot`。
5. 对每个成交对：
   - 核验买卖双方订单签名（同一订单首次出现时核验并缓存 `orderHash`）；
   - 核对资产、方向、市场、结算合约与订单一致；清算价不劣于双方限价；订单未过期、未在 L1 作废；
   - 核对 `filled[orderHash] + lots ≤ quantityLots`；
   - 以独立子调用原子执行：`transferFrom(卖方, 买方, 基础资产数量)`、`transferFrom(买方, 卖方, 计价金额)`、`transferFrom(买方, 手续费合约, 手续费)`；三项全成功才记 `filled`，任何一项失败则本对全部回滚，标记失败，并把失败方订单作废；
6. 成功的成交对，手续费记入撮合矿工的可领取余额（第 9.2 节），不在结算交易中向矿工逐个转账。
7. 写入 `lastSettledBatch`，并把本批结算结果（含失败成交对位图）追加到收件箱，供账本后续批次观察。

### 8.2 逐笔原子、批次不连坐

批次整体是否“有效”由档案证书决定；资金是否转移按成交对逐笔决定。这样既保留了每笔成交的原子性，又避免一个用户撤回授权就让整批成交失败、让市场停摆。

### 8.3 未结算深度上限

档案证书只确认撮合结果，资金在 L1 结算时才转移。为防止账本跑在 L1 前面太多，市场参数规定 `K_unsettled`：账本中已终局但 L1 未结算的批次数达到上限时，状态机拒绝新的撮合批次，只接受撤单和收件箱事件。矿工的手续费在结算后才入账，所以矿工有动力及时提交结算。

### 8.4 L1 不信任撮合委员会和档案组的什么

沿用 DLE 交易类的安全结论【DLE 现行】（DLE §4.7）：档案证书是结算的必要条件，但从不替代用户签名。即使撮合委员会和档案组同时被控制，也只能审查、延迟，或在用户签名允许的范围内选择成交；不能改价格、改数量、改资产、改收款人，也不能在没有订单签名的情况下转走任何资产。

这一结论不覆盖：用户私钥或合约钱包策略被盗；用户对恶意合约做了无限授权；结算合约自身的升级权限被滥用（第 13.3 节）。

## 9 手续费与矿工激励

### 9.1 费率与付费方

拆单和撮合由矿工完成，矿工按每笔成交额收取 **0.01%（1 bp）** 手续费【已决定】（2026-10-25）。

计费方式【本文拟议】：沿用 DLE 交易类的付费规则（DLE §13.2），按成交对计算，以计价资产收取，由买方支付：

\[
\text{fee} = \left\lceil \frac{\text{quoteAmount}}{10\,000} \right\rceil
\]

买方支付 `quoteAmount + fee`，卖方收到完整的 `quoteAmount`。下单时买方的订单签名已经承诺了这一费率版本（`feePolicyHash`），预检和占用也按含费金额计算。

是否改为买卖双方各付一半，列为待定（附录 B，B-4）。各付一半更对称，但卖方需要持有计价资产或从所得中扣除，舍入也更复杂。

### 9.2 分配【本文拟议】

手续费只分给为该批次做拆单与撮合工作的矿工：

| 份额 | 接收方 | 规则 |
| --- | --- | --- |
| \(\alpha\) | 批次组装者 | 负责收录、拆单、撮合计算 |
| \(1-\alpha\) | 投出接受票的其他委员会成员 | 平均分配 |

\(\alpha\) 由 DAO 投票设定，初始值【待定】（附录 B，B-6），本文演算取 30% 仅作示例。

整数规则沿用 DLE（DLE §13.4）：组装者份额向下取整，其余归验证者；验证者之间按签名地址升序分配零头，不留无主余数。手续费先记账、后领取：结算时只增加 `claimable[资产][矿工]`，矿工之后自行领取。领取失败不影响已结算的成交。

只有接受票被计入且批次已在 L1 结算的成员才分到手续费。投拒绝票、未投票、超时的成员不分。

### 9.3 成本由谁承担

【本文拟议】用户只付 0.01%，不再另付执行费。撮合矿工自行承担：

- 运行订单池、复算撮合的计算与带宽；
- L1 结算交易的 gas（由提交结算的人支付，通常是想尽快拿到手续费的矿工）。

这与 DLE 的现行做法不同。DLE 明确说明 1 bp 不足以覆盖执行成本，资产类转账另收执行准备金（DLE §13.1、§13.2a）。本文选择“一价全包”是为了让矿工的收入和成本都直接与成交额挂钩，代价是低成交额的交易对可能没有矿工愿意结算。设一个批次的 L1 结算成本为 \(G\)（折合计价资产），则批次保本成交额为：

\[
N_{\text{保本}} = \frac{G}{0.0001}
\]

例如 \(G = 0.005\) conet-USDC 时，一个批次至少需要约 50 conet-USDC 成交额。CoNET L1 上的实际结算 gas 尚未测量。是否另设执行准备金，列为待定（附录 B，B-7）。

### 9.4 收入测算

| 交易对日成交额 | 日手续费总额 | 组装者合计（\(\alpha\)=30%） | 其余委员会成员合计 |
| --- | --- | --- | --- |
| 10 万 | 10 | 3 | 7 |
| 100 万 | 100 | 30 | 70 |
| 1,000 万 | 1,000 | 300 | 700 |
| 1 亿 | 10,000 | 3,000 | 7,000 |

单位为计价资产（例如 conet-USDC）。这些数字只说明手续费与成交额成正比，不是收益预测。矿工每次被抽中的概率、每批成交额、结算成本和计价资产价格都会改变单个矿工的实际收入。

### 9.5 激励是否对齐

- **收录**：多收录可成交订单就多收手续费，遗漏订单等于放弃收入（第 6.2 节）。
- **撮合**：撮合是确定性的，矿工无法通过改变撮合结果多收费。批量竞价以成交量最大为目标，与按成交额收费方向一致。
- **结算**：手续费在 L1 结算后才入账，矿工有动力及时提交结算。
- **对敲**：费率很低，对敲刷量的成本也很低。矿工若自己对敲，只是付手续费给委员会其他成员，没有净收益；但第三方可以用低成本制造虚假成交量（第 12 章）。

### 9.6 与 DLE 现行费用规则的关系【需 DLE 修订】

DLE 现行规则把 1 bp 协议费按 50% 档案组、50% 接受签名的验证者分配（DLE §13.4），并要求执行准备金和可用性预算单独记账。本文把 1 bp 全部分给撮合矿工，与 DLE 现行规则不同。市场类是新增类别，可以由 DLE 修订另定规则，但需要回答：

- 档案组为市场类账本提供重放、存储和历史服务，其成本由什么支付。本文建议由市场创建时缴纳的账本租金和可用性预算支付（DLE §13.4a），不从 0.01% 中分成；
- 是否仍保留 DLE 的 50/50 结构，只把“验证者”一侧定义为撮合委员会。

列为待定（附录 B，B-2）。

## 10 流动性提供与快速交易手续费【待讨论】

本章是运营方 2026-10-25 要求讨论的议题：由用户提供流动性，赚取快速交易手续费。本章给出问题、可选方案、本文建议和需要决定的事项，不构成已决定的规则。

### 10.1 问题

批量竞价的价格在批次终局时才确定。一笔订单从发出到知道成交价，至少要经过一次委员会投票和一次档案确认；DLE 的投票窗口上限是 30 秒（DLE §6.5），实际延迟未测量。对希望立即知道成交价的交易者（例如支付场景、套利者、应用内兑换），这个等待是成本。

另一方面，愿意承担价格风险的用户可以为这些交易者提供“立即锁价”的服务，并为此收费。这就是“快速交易手续费”的来源：流动性提供者承担从报价到成交之间的价格变动风险，吃单方为确定性付费。

### 10.2 方案对比

| 方案 | 做法 | 是否非托管 | 快在哪里 | 主要问题 |
| --- | --- | --- | --- | --- |
| **甲：仅挂单** | 流动性提供者只在簿中挂长期限价单，靠价差获利，不另收费 | 是 | 不更快 | 不满足“快速交易手续费”的要求 |
| **乙：承诺报价快速通道（本文建议）** | 流动性提供者签署限时有效的承诺报价；吃单方接受后，下一批次优先按报价成交；吃单方付快速费给流动性提供者 | 是 | 吃单方立即知道成交价，不必等批次竞价 | 流动性提供者面临“免费期权”风险；报价方余额不足时仍可能失败 |
| **丙：L1 直接成交** | 吃单方拿流动性提供者的签名报价直接在 L1 成交，不经过 DLE | 是 | 一笔 L1 交易即结算，最快 | 绕过撮合矿工与 DLE，0.01% 无人撮合，需另定矿工是否收费 |
| **丁：资金池做市** | 用户把资金存入池子，由池子按曲线或策略报价 | 否 | 即时 | 违反非托管原则；与 GB AMM 白皮书的资金池规则重叠 |
| **戊：挂单返佣** | 从 0.01% 中拿出一部分返给被成交的挂单方 | 是 | 不更快 | 与“0.01% 归撮合矿工”的决定冲突 |

### 10.3 本文建议：承诺报价快速通道（方案乙）

**报价。** 流动性提供者签署 EIP-712 承诺报价：

```text
FirmQuote {
    version, marketId, maker, side,
    priceTicks,          // 承诺成交价
    maxLots,             // 本报价最多成交量
    validUntilBatch,     // 最晚在第几个批次之前有效（以账本 nonce 计，确定性）
    fastFeeBps,          // 快速费率
    nonce, settlement
}
```

报价经 L0 发给接单矿工，在订单池中公开。

**吃单。** 吃单方签署快速通道单：引用一个报价的哈希（或注明“任一不劣于某价的报价”），带最差价格和可接受的最高快速费率。接单矿工验证报价未过期、报价方在最近 L1 区块的余额与授权足够后，回执“已锁价”。

**成交。** 下一个批次先执行快速通道成交，按报价价格成交，再对剩余订单做批量竞价。快速通道成交不参加当批竞价。

**费用。**

| 费用 | 付费方 | 接收方 | 费率 |
| --- | --- | --- | --- |
| 撮合手续费 | 吃单方 | 撮合矿工 | 0.01%【已决定】 |
| 快速交易手续费 | 吃单方 | 流动性提供者 | `fastFeeBps`，由报价方设定，受 DAO 上限约束（【待定】） |

**结算。** 与普通成交相同，逐笔原子转账，资金始终在双方钱包。

### 10.4 风险与限制

- **“快”的边界**：快速通道让吃单方立即锁定价格，但资金仍在批次终局和 L1 结算时才转移，最终确认时间与普通成交相同。不能把“已锁价”显示成“已结算”。
- **免费期权**：报价在 `validUntilBatch` 之前有效。市场价格不利于报价方时，吃单方会选择成交；有利时不会。报价方需要用快速费、较短有效期或较宽价差覆盖这个风险。
- **撤销报价的竞态**：报价方可以发链下撤销，但撤销与吃单可能被收进同一批次。规则需要固定：同一批次中先执行吃单还是先执行撤销。本文建议先执行撤销，保护报价方；吃单方的“已锁价”回执因此不是绝对保证，界面需说明。
- **报价方余额不足**：报价方可以在锁价后转走资金，使成交失败。按第 4.5 节处理，并对报价方记录失败次数，频繁失败者限制报价。
- **组装者与报价方合谋**：组装者若同时是报价方，可能选择性收录吃单。快速通道单同样适用 L1 收件箱强制收录，但成本较高。是否禁止组装者在同一批次执行自己的报价，列为待定。
- **与 GB 规则的关系**：快速通道是用户之间的点对点成交，不涉及国库，不铸造或注销 GB，不改变 GB AMM 白皮书的资金池与 AMO 规则（第 14 章）。

### 10.5 需要决定的事项

1. 是否采用方案乙；或选择其他方案，或首版不设快速通道（附录 B，B-9）。
2. 快速费率由报价方自定（设 DAO 上限）还是由 DAO 统一设定（B-10）。
3. 报价有效期的上限，以批次数计（B-11）。
4. 同一批次中撤销报价与吃单的先后顺序（B-12）。
5. 普通挂单的流动性提供者是否也获得某种奖励。若获得，资金来源是什么；本文不建议增发任何代币作为奖励（B-13）。

## 11 性能与并行

- **交易对之间并行**：每个交易对是独立账本，由各自的委员会推进，互不排队【DLE 现行】（DLE §3.1）。增加档案组可以承载更多交易对。
- **交易对内部串行**：同一交易对的批次按 nonce 顺序推进，单个热门交易对的吞吐受批次间隔限制。热门交易对不能靠拆成多个账本扩容，那会分散深度。
- **每批抽取新委员会的开销**：DLE 现行规则是每个区块重新抽取委员会（DLE §6.1）。对高频批次，抽取和传播会成为主要开销。本文建议研究让一个委员会连续服务若干批次，同时满足冷却与风险敞口规则；这需要 DLE 修订，列为待定（附录 B，B-14）。
- **不作吞吐和延迟承诺**：确认延迟取决于路由、委员会投票、档案确认和重试。本文不给出任何延迟或吞吐数字。上线前须分别测量“已收到”“已撮合”“已结算”三种延迟（研究页要求）。

## 12 安全与市场公平性

| 风险 | 本文的处理 | 剩余风险 |
| --- | --- | --- |
| 撮合者改价、改量、转走资金 | L1 逐笔核验签名与限价；无托管 | 用户私钥被盗；无限授权给恶意合约 |
| 抢跑、插队 | 批量竞价使批次内顺序无关；边际分配用不可预知的随机种子 | 组装者可以选择收录；看到大单后自己下单仍可能 |
| 审查 | L1 收件箱强制收录；多矿工接单；委员会轮换 | 链上提交成本较高；短时延迟无法消除 |
| 委员会或档案组被控制 | 只能在用户签名范围内选择成交；L1 核验 | 审查、延迟；在限价范围内的不利成交 |
| 委员会作恶的规模 | 每批上限 `B_max`；DLE 委员会累计敞口 \(E_C\le E_{\max}\) | 参数未定 |
| 双签、伪造批次 | DLE 的双签罚没、档案组独立重放 | 依赖档案组诚实多数 |
| 数据扣留 | DLE 数据可用性：签名前必须重建并复算完整批次 | — |
| 成交失败（余额或授权不足） | 逐笔原子、不连坐；失败方订单作废、限制挂单 | 守约方错过成交 |
| 恶意代币 | 上市条件拒绝异常转账行为（第 4.3 节） | 代币升级后改变行为，需熔断 |
| 跨链资产风险 | 跨链证明须能拒绝伪造消息后才可上市；路由异常时熔断 | — |
| 对敲刷量 | 同地址自成交防护 | 不同地址对敲无法识别；成交量统计应标注 |
| 订单池垃圾订单 | 最小订单量、每地址挂单上限、失败计数 | 是否设挂单保证金待定 |
| 隐私 | L0 降低 IP 暴露 | 订单簿和结算公开，交易不匿名 |

档案组相关的生产阻塞项（第二套独立实现、生产网络、密钥托管等）关闭之前，以上依赖档案证书的安全结论都不成立【DLE 现行】（DLE §5.2.1，档案一致性规范 §11）。

## 13 治理

### 13.1 市场上市与参数【本文拟议】

- 新交易对上市、退市、熔断与恢复，以及 `lotSize`、`tickSize`、`B_max`、`priceBandBps`、`K_unsettled`、\(\alpha\)、快速费上限等参数，由 DAO 提案投票决定。
- 参数变更须指定未来生效的批次或 L1 区块，并说明已挂订单如何处理。手续费规则变更不追溯已签名订单：订单签名承诺了 `feePolicyHash`，结算按订单承诺的版本收费；新版本只适用于新订单。

### 13.2 无管理员

结算合约不设管理员角色，不设可以转移用户资产、修改订单记录或改动已入账手续费的特权地址【本文拟议，参照 GB 体系“所有 admin 都不存在，并入 DAO 管理”的决定】。

### 13.3 结算合约升级

结算合约持有大量用户授权，其升级权限等同于全部授权额度的控制权。本文建议：v1 结算合约不可升级；新版本以新地址部署，用户重新授权后迁移。若 DAO 决定保留升级能力，须采用固定地址代理、DAO 投票并附代码哈希、公开时间锁，并允许用户在生效前撤回授权。列为待定（附录 B，B-15）。

## 14 与 GB 经济规则的关系

- 本交易所只在用户之间撮合已存在的代币，不铸造、不注销任何代币，不持有储备，不改变 GB 的打造、退出、官方汇率 R 或覆盖率规则。

## 附录 C 一个批次的完整示例

交易对 GB / conet-USDC，参数按第 5.4 节示例。手续费分配取 \(\alpha=30\%\)。所有数字仅为演算。

**批次输入**

| 订单 | 方向 | 数量（GB） | 限价 | 来源 |
| --- | --- | --- | --- | --- |
| Carol | 卖 | 1,000 | 0.0100 | 簿中挂单 |
| Dave | 卖 | 2,000 | 0.0102 | 簿中挂单 |
| Erin | 买 | 1,500 | 0.0098 | 簿中挂单 |
| Bob | 卖 | 500 | 0.0097 | 本批新单 |
| Alice | 买 | 2,500 | 0.0102 | 本批新单 |

**清算价**

| 候选价 | 需求 \(D\) | 供给 \(S\) | 可成交 \(V\) |
| --- | --- | --- | --- |
| 0.0097 | 4,000 | 500 | 500 |
| 0.0098 | 4,000 | 500 | 500 |
| 0.0100 | 2,500 | 1,500 | 1,500 |
| 0.0102 | 2,500 | 3,500 | 2,500 |

清算价 0.0102，成交 2,500 GB。

**分配**：Alice 买入 2,500 GB 全部成交。卖方按价格优先：Bob 500（限价 0.0097）、Carol 1,000（0.0100）全部成交；Dave 位于边际价位，成交 1,000，剩余 1,000 留在簿中。Erin 限价低于清算价，不成交，继续挂单。Bob 和 Carol 以 0.0102 成交，获得价格改善。

**成交对与手续费**

| 成交对 | 数量（GB） | 计价金额（conet-USDC） | 手续费（conet-USDC） |
| --- | --- | --- | --- |
| Alice ← Bob | 500 | 5.1 | 0.00051 |
| Alice ← Carol | 1,000 | 10.2 | 0.00102 |
| Alice ← Dave | 1,000 | 10.2 | 0.00102 |
| 合计 | 2,500 | 25.5 | 0.00255 |

Alice 共支付 25.50255 conet-USDC；Bob、Carol、Dave 分别收到 5.1、10.2、10.2 conet-USDC。

**手续费分配**（以 conet-USDC 最小单位计，合计 2,550）：组装者 765；其余 5 名投接受票的成员各 357。

**若 Carol 在结算前撤回了授权**：Alice ← Carol 这一对失败，不转账、不收费，Carol 的订单作废；Alice ← Bob 和 Alice ← Dave 照常结算。账本在后续批次观察到结算结果后，恢复 Alice 剩余的 1,000 GB 买量，继续挂单。

**快速通道示例（方案乙，假设）**：Frank 签署报价，卖出至多 3,000 GB，价格 0.0103，快速费 0.02%。Gina 接受，买入 1,000 GB，立即得到锁价回执。下一批次先执行这笔成交：Gina 支付 10.3 conet-USDC 给 Frank，快速费 0.00206 给 Frank，撮合手续费 0.00103 给撮合矿工。快速费率仅为示例。

## 附录 D 术语

| 术语 | 含义 |
| --- | --- |
| 市场类账本 | 本文提出的第四类 DLE 账本，一个交易对一条，记录订单簿与撮合结果，不持有资金 |
| 撮合批次 | 市场类账本的一个区块，含一批订单输入与确定性撮合结果 |
| 撮合委员会 | 每个批次由 DLE 抽取的 7 名验证矿工，负责拆单与撮合 |
| 批次组装者 | 委员会中按抽签顺序排第一的成员 |
| 档案证书（AC） | 档案组 4/5 预提交签名，批次终局的唯一依据 |
| 成交对 | 一个买单与一个卖单之间的一次成交，L1 结算的最小原子单位 |
| L1 收件箱 | 结算合约中按序记录的链上撤单、链上订单和结算结果，账本必须按序处理 |
| 承诺报价 | 第 10 章快速通道中流动性提供者签署的限时可成交报价 |
